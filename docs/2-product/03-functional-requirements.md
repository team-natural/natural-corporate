# 03-functional-requirements.md — 機能要件定義テンプレート

## このセクションの目的

提供すべき機能、MVP スコープ、受け入れ条件、非機能要件を定義する。本テンプレートは 00_README §0-1 の**パターン A**（コンテンツ主体サイト + 軽量な管理画面）を前提とする。マルチテナント・サブスク課金・Platform 階層管理・チャット/リアルタイム通信を前提とした機能グループ（Organization 管理、プラットフォーム管理、チャット機能）は持たない。

## 0-H. ハイブリッド編集ガイド（要点）

- 推奨モード: Hybrid（AI 草案 + PdM 主導で確定）
- 人間確認必須: MVP 判断、優先度、非機能数値、受入条件の妥当性

## 3. ユーザーストーリー（主要のみ）

実装済みの導線から復元したもの。**関連 KPI は BIZ-02 が未記入のため空欄**。

### US-01 訪問者が診断から相談に至る

- **As a** AI・DX を進めたいが何から始めればよいか分からない企業の担当者
- **I want** 2 分程度の設問に答えて自社の現在地と次の一手を知り、その内容を持ったまま相談したい
- **So that** 何を相談すればよいかが整理された状態で問い合わせできる
- 関連機能 ID: F-08-02 〜 F-08-05, F-09-06, F-09-01
- 備考: 結果ページの CTA は `?inquiry-type=診断結果について&message=...` を付けて `/contact/` を開き、フォームまで自動スクロールする

### US-02 訪問者が事業内容を確認して問い合わせる

- **As a** システム開発の委託先を探している担当者
- **I want** 事業内容・実績・会社の信頼性（拠点・認証）を確認してから連絡したい
- **So that** 発注先として妥当か判断できる
- 関連機能 ID: F-02-01, F-02-03, F-02-04, F-02-06, F-09-01

### US-03 開発者がお知らせを追加する

- **As a** 自社の開発担当者
- **I want** Markdown を 1 ファイル追加するだけでお知らせを公開したい
- **So that** 管理画面を用意・運用しなくても情報発信できる
- 関連機能 ID: F-02-07, F-02-08
- 備考: `packages/content/news/<ファイル名>.md` の追加と `public/sitemap.xml` への追記の 2 手。**ファイル名がそのまま公開 URL になる**

### US-04 セミナー告知を出す

- **As a** 自社の開発担当者
- **I want** お知らせに `category: セミナー` を付けるだけで、セミナーページの開催実績にも載せたい
- **So that** 二重管理をしなくて済む
- 関連機能 ID: F-02-05, F-02-07

## 4. MVP スコープ定義

### 4-1. MVP 含有判断ルール

- MVP `○` = 実装対象（優先度 High / Medium は着手順を表す）
- High 優先度で MVP `△` は MVP 検証後に追加実装
- Medium / Low はベータ後の改善サイクルで判断

### 4-2. 含める機能（要約）

本サイトは **MVP 期を過ぎており、すでに公開・運用中**。2026-09 に行ったのは基盤の移行であって機能追加ではない。以下は「現に稼働している機能」の一覧として読む。

- 公開コンテンツ表示（FG-02: F-02-01 〜 F-02-11）
- 診断（FG-08: F-08-01 〜 F-08-05）
- お問い合わせ（FG-09: F-09-01 〜 F-09-07）
- 通知（FG-06: F-06-01, F-06-02）

同梱しているが稼働していないもの: 認証（FG-01: F-01-01 のみコードあり）、管理画面（FG-04）、会員登録・マイページ（FG-07）。

### 4-3. 除外項目と理由

| 除外機能 | 理由 | 将来再評価タイミング |
| --- | --- | --- |
| お問い合わせの DB 保存・管理画面での対応管理 | 移行時は現行動作の再現を優先した（GOV-01 D-005） | メール運用で対応漏れが起きた時点。GOV-02 TBD-02 |
| お知らせの管理画面編集 | 更新者が開発者である限り Content Collections で足りる（GOV-01 D-008） | 非開発者が更新するようになった時点 |
| 会員機能（登録・マイページ） | サイト上に会員向けに提供するものがない | GOV-02 TBD-01 |
| AI 機能 | サイト自身に LLM を要する機能がない（PRD-05） | — |
| 軽量 EC・決済 | サイト上で販売するものがない | — |
| お知らせの検索・カテゴリ絞り込み | 8 件規模では一覧で足りる | 件数が増えた時点 |
| 診断回答の保存・分析 | 回答をサーバーに送らない設計（クライアント完結） | 回答傾向を分析したくなった時点 |
| 多言語対応 | 日本語単一（DEV-01 §1）。海外拠点はあるがサイトの対象読者は国内 | — |
| Organization 管理・多階層ロール | 単一運営が前提（PRD-01 §1-2） | マルチテナント要件が出たら別テンプレートへ |

## 5. 受け入れ条件フォーマット

Given / When / Then の 3 要素で記述する。

```
Given <前提条件>
When <ユーザー操作>
Then <期待結果>
And <追加の期待結果>
```

例：

```
Given editor 権限を持つ AdminUser が管理画面にログインしている
When 記事編集画面で本文を入力し「公開」ボタンを押す
Then 公開側の記事一覧の先頭に新しい記事が表示される
And 記事（Post）の status が published に更新される
```

| 性能 | `/api/contact/` の応答 | **要記入** | Turnstile の `siteverify` と Resend への 2 回の送信に律速する |
| スケール | 同時接続 | **要記入** | 静的配信が主のため、Worker 側の負荷はお問い合わせ送信数に比例する |

可用性（稼働率）の数値目標は **PRD-02 §5-2 を正本** とし、本書では再掲しない（公開側と管理側で目標が異なり、公開側の方が優先度が高い点に注意）。

### 6-2. セキュリティ

詳細は **DEV-02** を参照。DEV-02 も本書と同じ admin / editor の単一階層・少数ロール（PRD-01 §1-2）を前提とする。

- 認証: 管理画面ログイン（FG-01）が標準。方式は D1 セッション + httpOnly 署名クッキー、ハッシュは Web Crypto PBKDF2（DEV-01 §2、DEV-02 §1-1、決定済み）。利用者向けの公開認証は FG-07（会員登録・マイページ）採用時のみで、AdminUser とは完全に別系統（DEV-02 §1-2）
- ロール: admin / editor の単一階層・少数ロール（PRD-01 §1-2）
- データ分離: マルチテナントではないため `organization_id` 等のテナントスコープは不要（PRD-02 §2）
- 監査ログ: 採用する場合は AdminUser の権限変更・Post の公開/削除等の重要操作を記録対象とする。記録先は DEV-01 §2「監査ログ」/ DEV-07 §4-4「activity_log」を参照（単一運営前提のため `organization_id` 等のスコープ列は持たない）

### 6-3. 保守性

- デプロイ頻度: 週 1 回以上を安全に実施可能
- 主要修正のリードタイム: 1 日以内
- バージョン更新: セキュリティパッチは重大度に応じて適用（運用は OPS-02）
